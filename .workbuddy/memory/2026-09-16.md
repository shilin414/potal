### 前端 P0 修复：定时任务飞书投递 `target_type` 丢失（另一并行会话遗留已收口）
- **症状**：定时任务弹窗里选了「投递目标」，创建后 `POST /api/v2/schedules` 返回
  `delivery target_type must be user or chat`（编辑保存 PATCH 同样中招）。
- **根因**：`ScheduleEditorModal.handleOk` 用 `await form.validateFields()` 的返回值拼 payload。
  rc-field-form 的 `validateFields()` / `getFieldsValue()`（**不带 `true`**）只返回**已注册 Form.Item
  的路径**（内部按注册路径 `cloneByNamePathList` 重建对象）；投递只注册了 `deliveries[0].target_id`，
  于是 `target_type` / `target_name` 被静默丢弃；`misfire_policy` / `deadline_policy` /
  `execution_window_seconds` 没有 Form.Item → 同样丢失（此前只是靠后端默认值蒙对）。
- **诊断要点（别被误导）**：浏览器/测试里看到的"值被回滚"是假象——store 本身一直是对的
  （`getFieldsValue(true)` 可见三元组齐全），丢失发生在**读值时**。把 store 写入序列打出来即可区分
  「写入被覆盖」与「读值丢字段」两类问题。
- **修复**：弹窗新增 `readValues()` = 先 `validateFields()` 只做校验，再 `getFieldsValue(true)` 取全量；
  `handleOk` 与 `refreshPreview` 统一走它（创建/编辑两条路径一起修好）。
- **验证（自证 + 反证）**：无头 jsdom 渲染弹窗、真实点击 antd Select 选项、抓
  `createSchedule`/`updateSchedule` 的真实 payload → 报文含
  `deliveries:[{target_type:"chat",target_id,target_name,content_mode}]`；
  反证（把 `readValues` 还原成旧写法）→ **两条用例同时 FAIL**，报文正好退回 `[{target_id,content_mode}]`。
