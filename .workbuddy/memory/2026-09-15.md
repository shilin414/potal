## 复审二轮修复（2026-09-15，同日）

复审报告基线 `418f2f18`；**P0×1 + P1×5 + P2×3 全部关闭**。

### 关键教训（务必记住）

- **P0：`AuthorizeExecution` 重建 Binding 时漏 `timeout_seconds`/`config`/`capabilities`**，
  而 `Binding.Snapshot()` 无条件写这三个字段 → 每个 Run 的 snapshot 变成 0/null →
  异步执行立即 poll timeout、交互执行超时被砍到 lease。**任何重建 Binding 的路径都必须与
  `bindingFromRow` 字段完全一致**（现在是 `bindingFromExecutionAuthRow`，有回归测试锁定）。
- **P1：provider kill switch 靠 `provider_id` 是 fail-open** —— `bindingFromInput` 从不写
  `provider_id`（实测库里 18 个 binding 有 16 个 NULL）。已改为**按 `provider_key` 匹配 + 失败关闭**，
  创建/更新时写入 provider FK，并加迁移 `0016` 回填。
- **P1：`admitOne` 曾在 schedule 行锁之外解析 binding** → PATCH application A→B 会写出
  `application_id=B` 但 `runtime_binding_id/provider/snapshot=A` 的自相矛盾 Run。
  原则：**任何影响 Run Snapshot 的事实都必须在最终 Admission Lock 之后读取**。
- **P1：Conversation 硬删会打断 scheduled Run / pending Delivery**（occurrence.run_id 孤链、
  delivery 读 `run.Output` 失败）。已下沉为 `execution.DeleteConversationCascade`（单事务）+
  守卫：活跃 Run 409；存在 `trigger_type='scheduled'` 的 Run 或有 `delivery_executions` → **拒绝硬删**。
  未做 Conversation 软删除（需改造 Sidebar/消息读取/分享/SSE），留作下轮。
- **P1：用户限流曾每请求 `NewRateLimiter`** → Redis 故障降级状态每次归零 = fail-open。
  现为长生命周期 limiter + `AllowKey(ctx,key)` + **每键有界本地状态 map**（4096 上限），
  并加了 **nil Redis 保护**（此前 nil rdb 会 panic）。outstanding 上限改为
  `CreateRunAdmitted`：**users 行锁 → 计数 → 同事务建 Run**（锁序恒为 users→conversations）。
- **P2**：TriggerNow 全程用 DB now；Schedule Update 执行权按 `cur.OwnerUserID` 校验（不是管理员）；
  Schedule 配额在用户行锁内原子；**Schedule 软删除不再物理删 `schedule_deliveries`**（消除
  deliveries→schedules 与调度器 schedules→deliveries 的锁序反转，保住旧 occurrence fallback）。
