### 关键教训（务必记住）

- **P0：`AuthorizeExecution` 重建 Binding 时漏 `timeout_seconds`/`config`/`capabilities`**，
  而 `Binding.Snapshot()` 无条件写这三个字段 → 每个 Run 的 snapshot 变成 0/null →
  异步执行立即 poll timeout、交互执行超时被砍到 lease。**任何重建 Binding 的路径都必须与
  `bindingFromRow` 字段完全一致**（现在是 `bindingFromExecutionAuthRow`，有回归测试锁定）。
- **P1：provider kill switch 靠 `provider_id` 是 fail-open** —— `bindingFromInput` 从不写
  `provider_id`（实测库里 18 个 binding 有 16 个 NULL）。已改为**按 `provider_key` 匹配 + 失败关闭**，
  创建/更新时写入 provider FK，并加迁移 `0016` 回填。
- **P1：`admitOne` 曾在 schedule 行锁之外解析 binding** → PATCH application A→B 会写出
  `application_id=B` 但 `runtime_binding_id/provider/snapshot=A` 的自相矛盾 Run。
  原则：**任何影响 Run Snapshot 的事实都必须在最终 Admission Lock 之后读取**。
- **P1：Conversation 硬删会打断 scheduled Run / pending Delivery**（occurrence.run_id 孤链、
  delivery 读 `run.Output` 失败）。已下沉为 `execution.DeleteConversationCascade`（单事务）+
  守卫：活跃 Run 409；存在 `trigger_type='scheduled'` 的 Run 或有 `delivery_executions` → **拒绝硬删**。
  未做 Conversation 软删除（需改造 Sidebar/消息读取/分享/SSE），留作下轮。
- **P1：用户限流曾每请求 `NewRateLimiter`** → Redis 故障降级状态每次归零 = fail-open。
  现为长生命周期 limiter + `AllowKey(ctx,key)` + **每键有界本地状态 map**（4096 上限），
  并加了 **nil Redis 保护**（此前 nil rdb 会 panic）。outstanding 上限改为
  `CreateRunAdmitted`：**users 行锁 → 计数 → 同事务建 Run**（锁序恒为 users→conversations）。
- **P2**：TriggerNow 全程用 DB now；Schedule Update 执行权按 `cur.OwnerUserID` 校验（不是管理员）；
  Schedule 配额在用户行锁内原子；**Schedule 软删除不再物理删 `schedule_deliveries`**（消除
  deliveries→schedules 与调度器 schedules→deliveries 的锁序反转，保住旧 occurrence fallback）。

## 第七轮推送 → CI 首轮红 → 根因定位与修复（2026-09-15，同日）

三件套提交 `39d668d` + `4e40cc8` 推送后：`check` job 全绿（含 `-race`），`integration` job 在
"integration tests" 失败。注解给出的失败点是**既有测试**：`TestExecutionFencingMatrix/slot_renew/current_owner`
→ `execution: provider inflight slot lost`，而该槽位存在且归属正确。本机同一套件连跑 10 次全过。

### 根因（探针证实）

**MySQL 的 `UPDATE` 返回 CHANGED rows，不是 matched rows。** 续约语句
`SET heartbeat_at = CURRENT_TIMESTAMP(3), expires_at = CURRENT_TIMESTAMP(3)+lease`：
续约与建行落在**同一毫秒**时两条语句算出的值完全相同 → 行被匹配但无列变化 → `RowsAffected = 0`，
与"行不存在"不可区分。调用方把 0 读成所有权丢失：

- `ProviderSlots.Renew` → `ErrProviderSlotLost`（CI 报错点）
- `slots.acquireOnce` 幂等分支 → 同一判定（原注释称 "unreachable"，实测**可达**）
- `HeartbeatOwned` / 合并心跳 → `ok=false` + `RunOwnershipLostTotal`，**worker 会放弃健康的 Run**

CI 的 MySQL 在 runner 本地回环（百微秒级），两条续约服务端间隔可 <1ms；本机 LAN 往返 1–3ms 必然跨
毫秒 —— 这就是"本地全绿、CI 红"的全部原因。

探针输出：行满足谓词 `COUNT=1`，`RowsAffected=0`；值不同时为 1；**`LAST_INSERT_ID(id)` 偏方在此形状下无效**。

### 修复与测试

- 三条续约语句（`HeartbeatLease` / `HeartbeatLeaseFenced` / `TouchProviderSlot`）的 `heartbeat_at`
  改单调写 `GREATEST(CURRENT_TIMESTAMP(3), DATE_ADD(heartbeat_at, INTERVAL 1000 MICROSECOND))`：
  与 stored 恒不相等 → changed == matched 重新成立。**Go 代码零改动**。
- 刻意不用 `GREATEST(expires_at, …)`：那会让过期时间逐次累加漂移，崩溃恢复窗口可能无界。
- 刻意不用 `ClientFoundRows=true`：会同时改变 `BindAgentThreadSessionOwned`（靠 changed-rows 区分
  "幂等重绑"与"换会话"）和 delivery 的重复检测语义，属全局变更。
- **`SET timestamp = <second>` 能把 session 时钟钉死**（`CURRENT_TIMESTAMP(3)` 变成 `.000`）→ 配上
  `MaxOpenConns(1)` 让所有查询复用同一条连接，就把"恰好同一毫秒"从运气变成**确定性条件**。
  测试 `TestLiveRenewalReportsOneChangedRow` 据此写成；**反证已做**：还原旧 SQL → 确定性 FAIL

### 缺陷本质（值得记进长期记忆）

`HeartbeatOwnedWithSlot` 在 slot 续约失败时**只记日志 + 单边 commit Run lease 续约**，返回 `true,false,nil`。
后果不是 metrics 问题而是 safety contract 破裂：Worker 继续调 provider，但 capacity accounting 已释放该 slot，
下一次 admission 数到 `depth = max-1 < max` 就放行新 Run → 真实并发 `max_inflight + 1`。
第七轮的同毫秒 `RowsAffected` 修复**没解决这条**，但它正是让 `0 changed rows` 成为强语义（"真的不在了"）的前提。

### 改了什么

- `service.go`：进入 provider execution 后（`slot != nil`）只有四个出口 —— `(true,true,nil)` 一次 commit /
  `(false,false,nil)` lease fence 被拒 / `ErrProviderSlotLost`（往返成功但 0 changed rows）/ 普通 error。
  **任何 slot 失败都连同 lease 续约一起 ROLLBACK**。`slot.Provider == ""` 从「commit + slotOK=false」改成整事务回滚 + error。
  仍然 XX-only，绝不 recreate slot（被释放的 capacity 可能已被新 admission 吃掉；recreate 会把 heartbeat 拖进完整 admission 锁序）。
- `worker.go`：`shouldCancelAfterHeartbeat(leaseOK, slotOK, err, deadlineElapsed)` ——
  `ErrProviderSlotLost` 立即 cancel；其他 error 仍按「最后一次已确认 TTL」fail-closed；`err==nil` 时 `!leaseOK || !slotOK` 都 cancel。
  确认丢失后**只做 local cancel + 幂等 Release，不 requeue**（provider 请求可能已发出，requeue 会重复提交），
  Run lease 留给 reaper 收敛。旧代码末尾那段「只记 telemetry 的 `if !slotOK`」成了不可达分支，已删。

### 自己写出来、提交前修掉的一个缺陷（教训）

`confirmedProviderSlotLoss` 最初写成 `err == nil && !slotOK`。但 **lease fence 被拒时 slotOK 也是 false**
（那次 slot 根本没被碰过）→ 会把「所有权丢失」误报成「容量丢失」，telemetry 与日志都指向错的子系统。
修法：谓词显式带上 `leaseOK` 维度，并把 cancel 文案抽成可测的 `heartbeatCancelReason(leaseOK, slotOK, err)`
+ 表驱动测试。**规律：多返回值 flag 在多个失败路径上都可能为 false 时，判定与面向人的文案必须带齐维度。**

## 第九轮专项整改（批次一–三）

### 做了什么

按第九轮报告的依赖顺序只做前三批（报告明确：Event Cursor 是 SSE Hub 的前置，Message 分页是前端虚拟列表的前置，硬塞七批会牺牲反证质量）。

- **P0-1 请求幂等**：迁移 0021 `run_requests`（PK user+client_request_id，UNIQUE run_id，`request_hash BINARY(32)`）。
  `CreateRunIdempotent` 三步：先解析 → 事务内 reserve（`ON DUPLICATE KEY UPDATE` 让重复报 0 changed rows 而非 1062）
  → 任何失败后再解析（并发重复的败者会输给自己的原请求的 user/conversation 锁，此时已提交的 reservation 证明请求已服务）。
  关键顺序：**幂等解析早于授权与准入**，否则首次请求已消费的附件 claim / outstanding 配额会把合法重放报成 400/429。
  handler 201 首创 / 200 重放 / 409 `idempotency_key_reused`。
- **P0-2 提交状态机**：迁移 0022 `provider_submissions`（state `sending|accepted|rejected|unknown`，key `potal:run:<uuid>:submit:<n>` 不含 attempt）。
  只有 `rejected` 允许重发；`sending`/`unknown` → `ErrProviderSubmitUnknown` → park `waiting_external`。
  `MarkSubmissionAcceptedOwned` 把 submission 状态与 `runs.external_run_id` 写在**同一事务**；re-claim 时 `claimed.Run.ExternalRunID` 或 submission 记录非空就**根本不调 provider**，改为 reconcile/poll。
  `waiting_external` 由 `ExpireParkedExternalRuns`（DB 时钟 − grace，默认 10min）收敛为 `failed/provider_submit_unknown`，
  worker scanLoop 每 tick 调一次——否则它是非 settled，会永久占 conversation（409）与配额。
- **批次二**：0023 `runs.next_event_sequence`（backfill `COALESCE(MAX+1,1)`），分配改 O(1)；event 读取加 LIMIT + `items/next_after/has_more`；
  SSE 网关逐页 replay，durable 帧写 `id:`、transient 不写，`query after > Last-Event-ID > 0`，前端 `lastDurableSequence` + 本地去重。
  顺带修掉：`WriteHeader` 后没 `Flush`，无事件可发的流会让客户端一直等不到响应头。
- **批次三**：`content.chunk` 只写 `text`+`offset`（原来每 chunk 带累计 snapshot，1MB 回答 ≈ 250MB 事件数据）。

### 反证（本轮最重要的产出之一）

脚本化：`backend-go/scripts/falsify_review9.sh`（16/16）、`frontend/scripts/falsify_review9.sh`（12/12）。
逐个临时还原修复 → 确认对应测试 FAIL → 还原 → 确认 PASS。

**反证当场抓到 2 个假测试**（断言写得对、但从未被执行）：

1. 前端 transient 游标测试把 transient 放在最前面，而那时游标本来就是 0，等价于没测；
   改成 durable → transient 顺序后才真正覆盖"哨兵不得回退游标"。
2. 前端重放去重测试的首次请求是**失败**的（没插入任何东西），`alreadyPresent` 分支从未执行；
   改为调用方显式持有 id 的重试路径。

**结论**：反证不是形式主义，它会暴露"测试通过 ≠ 修复被覆盖"。这是本轮唯一发现自身缺陷的手段。

### 处理既有测试的方式（值得记住）

`BeginProviderAttemptOwned` 被 `BeginProviderSubmissionOwned` 取代后，原有集成测试里"claim 后消费一次 attempt"的语义**不再成立**：
未决提交不允许再次 begin。这不是回归而是本轮的意图，于是：

- 新增 `beginSubmissionRefused` fixture helper，把"消费一次 attempt"表达成"provider **明确拒绝**后重试"，
  测试故事从"worker 死了"变成"provider 拒绝了然后 worker 死了"——更准确，且仍然覆盖 attempt 预算跨 reclaim 保留。
- 断言 `begin attempt 两次 = 1,2` 的用例改为断言新语义（第二次 begin 必须 `ErrProviderSubmitUnknown` 且不消耗预算），
  并单独覆盖 rejected 后重试（同 key、attempt=2）。

即：**既有测试的期望如果与新语义冲突，要判断是"新语义错"还是"旧期望记录了不安全的旧行为"**，后者要改期望并写明理由。
