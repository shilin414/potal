### 如何接入 / 切换 Aily 自定义智能体 ✅（2026-09-12）

**先纠一个常见误解**：智能体 id **不写死在代码里**，它是 TiDB 里的一条配置——`catalog_runtime_bindings.external_resource_id`（对应飞书 `agent_id`）。
`AILY_DEFAULT_AGENT_ID`（`backend/.env`）**只是 `bootstrap_runtime_catalog` 不传 `--agent-id` 时的默认值**，运行时并不读它。

**三条配置途径（改完即生效，无需改代码；web 进程都不用重启）**

| 途径 | 用法 | 适合 |
|---|---|---|
| **智能体市场 UI（2026-09-12 新增，推荐）** | `/agents` → 「新建智能体」→ 选运行时（飞书 Aily 自定义智能体）→ 填 Agent ID/身份模式/执行模式 → 可勾「设为工作台默认智能体」 | 日常自助 |
| Django Admin | `/django-admin/catalog/applicationruntimebinding/`；或「应用 → 运行时绑定」内联；改 `external_resource_id` 即换智能体 | 批量运维 |
| 管理命令 | `manage.py bootstrap_runtime_catalog --application-slug X --agent-id agent_xxx [--default]` | 首次部署 / CI |
| 排查命令 | `manage.py bootstrap_runtime_catalog --list` → 每个应用绑的是哪个 agent、谁在跑、谁是主智能体 | 排查"到底在跑哪个 agent" |

UI 途径等价于 ①②的组合：创建 `Application(kind=chat, renderer_key=chat)` + `ApplicationRuntimeBinding(provider_key=feishu_aily, runtime_type=agent, identity_mode=user, execution_mode=interactive)`，并可在卡片上随时「改头像 / 设为主智能体 / 编辑（换 Agent ID）/ 删除」。

**新增一个 Aily 智能体的完整步骤**
- **推荐**：`/agents` → 「新建智能体」→ 运行时选「飞书 Aily 自定义智能体」→ 填 Agent ID（可用「校验可见性」先探一次）→ 保存；第 2/3/4 步由接口在一个事务里完成
- 手动（Admin / 命令行）路径：
1. 飞书侧拿到 `agent_id`；确认该智能体对使用者可见（worker 每次会调 visibility 接口校验，UAT 调不可见的智能体会失败）
2. Admin 建 Application：`kind=chat`、`renderer_key=chat`、`is_public=True`
3. 在该应用的「运行时绑定」内联填：`provider_key=feishu_aily`、`runtime_type=agent`、`external_resource_id=<agent_id>`、`identity_mode=user`、`execution_mode=interactive`、`enabled` ✔
4. （可选）设为工作台主智能体：勾 `is_default_agent`，或用列表页动作「设为主智能体」
5. 前端零改动：新应用自动出现在首页「推荐」分组，智能体切换器可直接切

**切换主智能体**（架构文档 §38 的"默认主 Agent"）
- 智能体市场：卡片上的星标按钮（**2026-09-12 新增**，仅创建者/管理员可点）
- Admin：对目标应用执行「设为主智能体」（或勾 `is_default_agent`）
- 命令行：`manage.py bootstrap_runtime_catalog --application-slug X --default`
- 唯一性：`Application.set_default_agent()` 在事务里清掉其他应用的标记（TiDB 不支持条件唯一约束 models.W036，所以不用 DB 约束）；只有「kind=chat 且存在 enabled 绑定」的应用有资格，否则抛 ValidationError
- 切换只影响"新消息默认发给谁"，**不影响历史 Run**（Run 落的是 `runtime_snapshot`）
- 前端会在切换器里给主智能体显示「主」标记；未设置时回退到第一个有绑定的 chat 应用（`resolveDefaultApplication` 纯函数，有单测）

**同一次要并行用多个智能体**：一个 Application 只能绑一个 agent（`unique(application, runtime_type, provider_key)`），所以是"一个智能体 = 一个 Application"；切换器/首页天然支持多应用并列。

**本次顺带确认的现状**：`--list` 实测输出——
```
[1] creative-chat (创作助手, kind=chat, public=True) feishu_aily/agent:agent_4jz9pu9exyaws ← 主智能体
[3] wechat-article-writer (微信公众号文章生成, kind=chat, public=True) （无绑定：无法发起 Run）
```
即：**`wechat-article-writer` 目前没有绑定，因此不会出现在工作台里**（`GET /api/v2/applications` 只列有 enabled binding 的 chat 应用）。要启用它，按上面第 3 步补绑定即可。

**前端小修（本轮实测发现）**：首页输入框在目录尚未加载完就按 Enter 会被静默拒绝。现在按钮置灰、提示「正在加载智能体…」，且**不清空已输入文字**，加载完直接再按 Enter 即可（实测通过）。

17. **飞书 `authen/v1/user_info` 不返回 `user_id`**（实测，2026-09-12）：本应用当前 scope 下响应字段只有 `name/en_name/avatar_big|middle|thumb|url/open_id/union_id/tenant_key`，拿不到企业工号形态的 `user_id`（如 19127920）。因此聊天的 `user_id` 由 `User.display_id` 承载：能拿到时自动写、拿不到时 `manage.py set_display_id` / Admin 维护，永远有本地主键兜底。**别把展示值写进 `FeishuIdentity.feishu_user_id`**——那是身份匹配键，污染它会在飞书真返回该字段时造成用户误合并
18. **`session_user_payload` 是会话用户形状的唯一实现**：新增用户字段要**只改这一处**（登录/兑换/session/admin 四个接口都读它），否则会出现"飞书登录有、本地登录没有"的 `undefined`（与第 16 条同源问题）。前端持久化的 `user` 靠 `AppShell` 的 `syncSessionUser()` 追平，改字段名记得同步 `services/session.ts`

### 用户实测问题修复：SSE 全坏 + 市场 404 ✅（2026-09-12 第四轮）

### 用户实测问题修复：生成图片先裂开再展示 + 闪烁 ✅（2026-09-12 第五轮续）

**根因**（真实 run `01a09628…` 事件序列实证）：Aily 流式时 `content.delta`（seq 3，内含

**追修（用户 F12 复测：同一图片的 `/open` 302 + CDN URL 仍反复成对请求）**——两处根因：
1. **ReactMarkdown `components` 内联对象**：每次渲染都新建 `img`/`a` 组件函数 →
   React 视为不同组件类型 → `<img>` 子树整体卸载重挂 → 每个流式 delta 都重新走
   `/open` 302 → CDN 重新下载。修复：`components` 改为 `useMemo`（仅依赖 artifacts），

## 第七轮（2026-09-13）：定时任务 Schedule Core + 飞书投递 全栈落地

按《未来演进完整架构文档》当前阶段核心推进（ARCH 为准，G 清单为旧计划状态快照）。

### 链路

```
Schedule（结构化触发）
→ studio-scheduler 扫描 due（1s 间隔，纯 SELECT）
→ 单事务：Occurrence(UNIQUE schedule_id+scheduled_at) + Conversation + Message + Run + Outbox + next_run_at
→ 现有 Outbox → Redis Streams → CAS → Lease → Aily Worker
→ Run succeeded（CAS 赢家钩子）
→ DeliveryExecution（UNIQUE occurrence_id+schedule_delivery_id）+ Delivery Outbox
→ queue:feishu_delivery → Delivery Worker（GCRA + owner UAT → Feishu IM）
```

### 关键工程决策

1. **单事务原子性**：occurrence+run+outbox+next_run_at 同事务提交，Scheduler 任意点崩溃不留孤儿（无需 occurrence reaper）；`CreateRunInTx` 事务变体复用 execution 全部写入逻辑。
2. **幂等三层**：`(schedule_id, scheduled_at)` 唯一键（多 Scheduler 屏障）→ Run CAS（worker 层）→ `(occurrence_id, schedule_delivery_id)` 唯一键（投递层）。Redis 重启/重复消息均被 TiDB 吸收。
3. **TiDB DDL 约束实测**：multi-statement 批内后续语句看不到前面新增列/表，ALTER 的 AFTER 亦不能引用同语句新列 → runs 扩展拆 0006（列）/0007（索引）/0008（表）三个批次，单文件内语句互相自包含。
4. **优先级**：scheduled runs 落 `priority=scheduled_normal`，claim 索引对齐 ARCH `(status, available_at, priority, created_at)`，为 Interactive > Scheduled 的公平调度铺路。
5. **策略 v1 冻结**：misfire fire_once（next_run_at 单槽天然只补一次）、overlap queue/skip、deadline=scheduled_at+execution_window、run-now 建真实 occurrence 不动 next_run_at。
